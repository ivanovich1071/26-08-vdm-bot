# Бот-магазин для vdm.ru: Telegram + MAX на Cloud.ru

> Публичная версия плана. Коммерческие детали заказчика, технические подробности
> интеграции с сайтом и рабочий список вопросов ведутся во внутренних документах
> и в репозиторий не попадают.

## 1. Задача

Диалоговый бот в MAX и Telegram для интернет-магазина оборудования и учебных комплектов
для детских садов и школ. Бот консультирует по ассортименту, работает как продажник
по методике CJM, показывает карточку товара как на сайте, ведёт корзину и доводит клиента
до оплаты, счёта или передачи менеджеру. Языковые модели подключаются через Cloud.ru
Foundation Models, вся система разворачивается на Cloud.ru.

Аудитория смешанная: розничные покупатели и организации (включая бюджетные закупки),
поэтому сценарий завершения сделки не один.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Завершение сделки | Три подключаемые стратегии одновременно: онлайн-оплата, счёт с коммерческим предложением, заявка менеджеру. Конкретная комбинация включается конфигом |
| Мессенджеры | MAX — приоритетный канал, Telegram — обязательный второй. Ядро мессенджеро-независимое |
| Источник данных | Прайс-лист заказчика как основа, модуль актуализации с сайта как дополнение. При появлении штатной выгрузки (YML / CommerceML / 1С) она становится приоритетным источником |
| ФЗ-152 | Полный комплект: техническая реализация плюс пакет документов |

## 3. Архитектура

```
          Telegram Bot API                    MAX Bot API
                 │                                │
        adapters/telegram                 adapters/max
                 └──────────┬─────────────────────┘
                            ▼
                    core/  (мессенджеро-независимое ядро)
       диалог · корзина · каталог · заказы · согласия ПДн · UI-примитивы
                            │
        ┌───────────────┬───┴────────┬──────────────┬───────────────┐
        ▼               ▼            ▼              ▼               ▼
   agent/ (LLM)   catalog/ (поиск)  checkout/    privacy/       crm/
   Cloud.ru FM      FTS + trgm      3 стратегии   ФЗ-152      лид и КП →
                    (+pgvector)                  согласия      менеджер
        └───────────────┴────────────┴──────────────┴───────────────┘
                            ▼
       PostgreSQL 16 (товары, корзины, заказы, ПДн, журнал согласий) · Redis
                            ▲
                 ingest/ (сборка базы знаний из источников)
```

**Ключевой принцип:** адаптеры не содержат бизнес-логики. Ядро отдаёт абстрактный ответ
(`Message | ProductCard | ProductList | Keyboard | Invoice`), адаптер рендерит его в примитивы
своего мессенджера. Ограничения раскладки клавиатур в MAX (до 7 кнопок в ряду, до 3 для
кнопок-ссылок, геолокации и контакта) закладываем как общий потолок, чтобы интерфейс
совпадал в обоих каналах.

**Стек:** Python 3.12 · aiogram 3 · `max-botapi-python` · FastAPI (вебхуки, колбэки платежей,
админка) · SQLAlchemy 2 async · PostgreSQL 16 (`pg_trgm`, `pgcrypto`, опционально `pgvector`) ·
Redis 7 · APScheduler · Docker Compose.

## 4. База знаний

Канонический формат — JSON Lines (`data/kb/products.jsonl`) плюс дерево категорий.
Запись товара:

```json
{
  "sku_1c": "…",
  "external_id": 0,
  "name": "…",
  "url": "https://vdm.ru/catalog/…",
  "price": 0,
  "currency": "RUB",
  "in_stock": 0,
  "category_path": ["…", "…"],
  "description": "…",
  "images": ["…"],
  "attributes": {},
  "kit_contents": [],
  "sources": {"price": "…", "content": "…"},
  "updated_at": "2026-08-27T10:00:00+03:00"
}
```

Сборка идёт тремя слоями с явным приоритетом источников: прайс-лист — авторитет по цене,
остатку и артикулу; печатные каталоги — описания и состав комплектов; сайт — контент,
фотографии и актуальность. Мердж детерминированный, происхождение каждого поля сохраняется
в `sources`, расхождения между источниками попадают в отчёт, а не теряются молча.

## 5. Поиск по каталогу

В OpenAI-совместимом API Cloud.ru Foundation Models эндпоинта эмбеддингов нет, поэтому
основа — лексический поиск, вектор остаётся опцией:

1. Полнотекстовый поиск PostgreSQL (`russian`) по названию, описанию и пути категории
   с весами через `setweight`.
2. Триграммы (`pg_trgm`) по названию и артикулу — ловят опечатки и сокращения.
3. Фильтры: цена, наличие, раздел, нормативное основание закупки, возрастная группа.
4. Переранжирование топ-50 → топ-5 языковой моделью со строгой JSON-схемой ответа.
5. Опционально `pgvector` — включается конфигом, если embedding-модель окажется доступна.

Целевая метрика: top-5 hit rate ≥ 90 % на наборе из 50 реальных запросов менеджеров.
Замеряем **до** разработки агента — если поиск плохой, агент это не спасёт.

## 6. AI-агент

Клиент — OpenAI SDK с `base_url` Cloud.ru Foundation Models. API поддерживает вызов
инструментов, параллельные вызовы и `response_format: json_schema` — на этом строится агент.

**Два режима с общей памятью диалога:**
- **Консультант** — отвечает по ассортименту строго из базы знаний. Не знает — говорит
  «не знаю» и предлагает менеджера. Цену и наличие называет только из базы, с датой актуальности.
- **Продажник** — ведёт сделку по CJM: выявление потребностей → подбор решения → презентация
  продукта → обсуждение условий и оплаты → фиксация следующего шага → альтернативное
  предложение. Технические коды этапов живут только в JSON и никогда не показываются
  пользователю.

**Состояние сделки** фиксируется на каждом ходу строгой JSON-схемой: этапы CJM с оценками
и обоснованием, понимание клиента (цель, потребность, барьеры), текущий и следующий этап,
следующее действие, выбранный продукт, оффер, следующие вопросы. Используется при передаче
менеджеру и для аналитики.

**Инструменты:** `search_products`, `get_product`, `get_category_tree`, `add_to_cart`,
`update_cart_item`, `get_cart`, `start_checkout`, `create_quote`, `handoff_to_manager`,
`get_delivery_info`.

**Ограничения:** агент не изобретает товары, цены и сроки; действия с корзиной и заказом —
только через инструменты; оформление заказа и передача персональных данных — только после
явного подтверждения пользователем.

Промпты хранятся в `agent/prompts/` как версионируемые файлы с переключателем версий.
Их доработка — отдельная задача.

## 7. Корзина и оформление

Корзина живёт в базе и общая для каналов: один пользователь — одна корзина в MAX и Telegram.
Карточка товара рендерится как на сайте: фото, название, цена, наличие, кнопки количества,
«В корзину», ссылка на страницу товара.

`CheckoutStrategy` — интерфейс с тремя реализациями:
- **Онлайн-оплата** — платёжная ссылка провайдера и фискальный чек по 54-ФЗ, вебхук об оплате
  на FastAPI. Одна и та же ссылка работает в обоих мессенджерах: сознательно не используем
  встроенные платежи Telegram, чтобы не разводить два фискальных контура.
- **Счёт для организаций** — сбор реквизитов, генерация коммерческого предложения и счёта
  в PDF, отправка файлом в чат и менеджеру.
- **Заявка** — лид в CRM или на почту, без онлайн-оплаты.

## 8. Актуализация данных

Модуль периодически сверяет базу знаний с сайтом: цены, наличие, новые позиции, снятые
с продажи. Работает по расписанию (цены и остатки чаще, полная сверка реже), инкрементально,
с ограничением нагрузки и уважением к `robots.txt`, по письменному разрешению владельца сайта.
Результат каждого прогона — отчёт о расхождениях между источниками.

Тесты модуля работают на сохранённых страницах-фикстурах и не требуют сети.

## 9. ФЗ-152

Техническая часть:
- Персональные данные хранятся только в РФ, в отдельной схеме базы, доступ по ролям,
  TLS в транспорте, шифрование контактных данных, резервные копии в российском хранилище.
- Явное согласие до первого сбора данных: экран с текстом, кнопка, сохранение версии текста,
  времени и идентификатора в неизменяемом журнале согласий.
- Права субъекта прямо в боте: экспорт своих данных, удаление или обезличивание,
  автоочистка по истечении срока хранения.
- **Маскирование персональных данных перед отправкой в языковую модель**: имена, телефоны,
  адреса и почта заменяются плейсхолдерами до вызова и восстанавливаются в ответе.
  Это же чистит логи и трассировки.

Документарная часть готовится отдельным пакетом и передаётся заказчику для утверждения.

## 10. Развёртывание

Виртуальная машина Cloud.ru + Docker Compose: приложение (FastAPI и адаптеры), воркер
(актуализация данных и сборка базы знаний), PostgreSQL, Redis, nginx с TLS для вебхуков.
Секреты — в переменных окружения, вне репозитория. Мониторинг: healthcheck, метрики,
алерты на сбой актуализации и на расхождение цен.

## 13. Проверка

- **Сборка базы знаний:** отчёт с числом товаров, покрытием цен, описаний и фотографий,
  списком расхождений между источниками.
- **Поиск:** 50 реальных запросов менеджеров, замер top-5 hit rate до разработки агента.
- **Актуализация:** юнит-тесты на сохранённых страницах-фикстурах, без сети.
- **Бот:** сквозной прогон «вопрос → подбор → карточка → корзина → оформление» в обоих
  мессенджерах; отдельная проверка, что технические коды этапов CJM ни разу не попали
  в текст пользователю.
- **Оплата:** тестовый магазин платёжного провайдера, проверка вебхука и фискального чека.
- **ФЗ-152:** автотест на маскирование — в логах и в запросах к модели нет персональных
  данных; экспорт и удаление данных отрабатывают.
